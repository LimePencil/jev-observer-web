Jev Observer는 MIT 라이선스를 사용하는 독립 프로젝트입니다. 애플리케이션, 테스트, 문서, 호환성 검증에 기여할 수 있습니다. [소스 저장소](https://github.com/LimePencil/jev-observer), [개발 환경 설정](/ko/docs/development), [아키텍처](/ko/docs/architecture)부터 살펴보세요.

## 문제 보고하기 {#report-a-problem}

버전 또는 커밋, 운영체제, 관련 플래그, SDK 버전, 최소한의 재현 방법을 포함해 [이슈](https://github.com/LimePencil/jev-observer/issues)를 작성하세요. 기대한 동작과 실제 동작을 설명하세요.

수집 문제라면 전달 성공 여부와 상태 카운터 값을 포함하세요. 대시보드 문제라면 필터, 일시 중지 상태, 상세 패널이 열려 있었는지를 포함하세요. 합성 데이터를 사용하고, 로그나 캡처 또는 내보낸 파일을 공유하기 전에 비밀 값과 민감한 내용을 제거하세요.

## 데이터 처리 규칙 지키기 {#preserve-the-data-contract}

변경 범위를 명확하게 유지하고 다음 원칙을 지켜 주세요.

- 전달은 캡처 슬롯 예약이나 큐의 빈자리를 기다리지 않습니다. 기록 누락은 계속 확인할 수 있어야 합니다.
- 답변이 여러 개인 요청도 사용량과 비용은 한 번만 집계합니다. 없는 값은 알 수 없는 상태로 유지하며, 실패를 유효한 답변으로 바꾸지 않습니다.
- 변경된 정의, 질문 순서, 타입이 있는 Choice 값은 서로 구분할 수 있어야 합니다. 가져온 기록은 출처와 보고된 값을 유지합니다. Box 좌표를 스칼라 통계로 바꾸지 않습니다.
- 캡처 설정에서 제외한 인증 정보와 입력은 가져온 메타데이터를 포함해 저장된 기록에 남기지 않습니다. 알려진 입력 경로를 제거하기 전에 비밀 값을 찾아야 합니다. 모호한 민감 정보 마스킹이나 마스킹으로 바뀐 외부 가져오기 식별자는 작업 전체를 원자적으로 거부해야 합니다.

정규화나 가져오기를 변경할 때는 각 프로토콜과 모델 프로필을 대표하는 픽스처가 필요합니다. 프로토콜, 검증 방식, 인증 제공업체의 식별자를 분리해서 유지하세요. 전달 동작을 바꿀 때는 응답 바이트, 상태, 헤더, 중단된 전송을 검증하세요. 동작은 릴리스 소스와 테스트를 기준으로 확인하세요. 연구 계획에는 아직 출시되지 않은 제안이 포함될 수 있습니다.

## 검증하고 제출하기 {#verify-and-submit}

관련 [개발 검사](/ko/docs/development#run-the-checks)를 실행하세요. 대시보드를 변경할 때는 키보드 조작, 좁은 화면, 로딩 및 오류 상태, 알 수 없는 값, 상세 패널을 닫았다 다시 열 때 처리 중인 검토 작업을 확인하세요. 필터 범위, 일시 중지 동작, 독립적인 수집 상태를 유지하세요. 처리 중인 가져오기와 삭제도 패널을 닫았다 다시 열어도 유지되어야 합니다.

합성 브라우저 테스트, 패키지에 포함된 백엔드 통합 테스트, 실제 제공업체 검사는 각각 다른 사항을 검증합니다. 풀 리퀘스트에서 각 검사의 범위를 명확히 설명하세요. SDK 변경은 [호환성 검사](/ko/docs/development#reproduce-sdk-compatibility)를 따르세요. 성능 변경은 [벤치마크 절차](/ko/docs/development#measure-representative-load)에 따라 정확한 실행 파일, 호스트, 워크로드, 기록 크기, 수집 누락을 기록하세요.

애플리케이션 저장소에 풀 리퀘스트를 작성하세요. 문제, 변경 후 동작, 검증 결과, 남은 한계를 설명하세요. CLI 플래그, 가져오기 형식, API 동작이 바뀌면 공개 문서도 갱신하세요. 화면상의 변화를 설명하는 데 도움이 된다면 스크린샷을 포함하세요.
